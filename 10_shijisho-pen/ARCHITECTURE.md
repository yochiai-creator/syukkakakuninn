# 指図書 書き込み — 全体の構成と設計メモ

このファイル1つで、プロジェクトの全体像・主要ファイルの中身・設計判断が分かるようにまとめたもの。
細かい挙動は各ソースの先頭コメントと関数コメントに書いてある。食い違ったらソースが正。

- 最終更新: 2026-10-05
- GAS プロジェクト: `.clasp.json` の scriptId、ウェブアプリのデプロイ ID は「6. 運用」を参照

---

## 1. 何をするものか

出荷作業指図書(PDF)を、現場のタブレット(iPad + ペン)でチェックするための仕組み。
**1つの GAS プロジェクト**に、役目の違う2つの部品が同居している。

| 部品 | ファイル | 動き方 | 役目 |
|---|---|---|---|
| **振り分け** | `Sort.js` `MasterSeed.js` | 毎朝6時の時間主導トリガー(`runSort`) / エディタから手動実行 | 本社から届く指図書 PDF を読み取り(OCR)、容器サイズ別フォルダへ「出荷日_依頼No_出荷先.pdf」でコピーする。片付け(要確認への移動・重複の削除)もする |
| **書き込みアプリ** | `Code.js` `Index.html` | ウェブアプリ(組織内限定) | コピーをタブレットで開き、ペン・レ点・ハンコで書き込み、上書き / 別に保存 / チェック完了 する。作業指示一覧(簡易版)も出す |

2つは Drive 上のフォルダとファイル名の約束(→「4. データの持ち方」)でつながっている。
関数は同じグローバル空間にあるので、`Code.js` から `Sort.js` の関数(`buildSizeIndex_` など)を直接呼んでいる。

```
本社システム
   │ PDF を置く
   ▼
'002_出荷作業指図書/2026年/9月/出荷作業指図書_26.09.29_26-10719-0(4).pdf   ← 元(触らない)
   │ runSort(毎朝6時)… OCR → サイズ・得意先コード・数量などを読む
   ▼
◆容器種類別/20Ｋ/26.09.29_26-10719-0(4)_HE近畿 京都北.pdf                 ← コピー(作業用)
   │ タブレットのアプリで開いて書き込む
   ├─ 上書き保存 ……… 同じファイルを書き換え(途中保存の印)+ 棚に書き込み前PDFと書き込み一覧
   ├─ 別に保存 ……… …_書込.pdf を横に作る
   └─ チェック完了 … ◆チェック完了/2026年/10月/20Ｋ/(出荷日の月) に書き込み済みPDFを作り、コピーはゴミ箱へ
   │
   │ 出荷日を過ぎても残っているコピーは runSort が '004_要確認 へ移す
   ▼
'001_【出荷】/'004_要確認/
```

|---|---|---|
| `'002_出荷作業指図書/<年>年/<月>月` | `SRC_ROOT_ID`(Sort.js) | 元の指図書。本社から届く。**振り分けは読むだけで一切変えない** |

| `'001_【出荷】/'004_要確認` | `OVERDUE_FOLDER_ID`(Sort.js) | 出荷日を過ぎても未チェックで残っていたコピー |

## 4. データの持ち方(部品どうしの約束)

### 4.1 コピーのファイル名

```
26.09.29_26-10719-0(4)_HE近畿 京都北.pdf
└出荷日┘ └─ 依頼No ──┘ └ 出荷先(略称)┘
```

- 出荷日と依頼No は**元のファイル名から取る**(`出荷作業指図書_26.09.29_26-10719-0(4).pdf`)。OCR には頼らない
- 出荷先は得意先マスタの会社名(B列)。マスタに無ければ OCR の読みをそのまま使う
- 「コピー済みか」「チェック完了済みか」は、先頭の `出荷日_依頼No_` が一致するかで判定する(`alreadyCopied_`)。
  末尾の `_` まで見るので `26-60754-0_` が `26-60754-0(1)_` に当たることはない。出荷先部分は OCR で揺れるので見ない
- 別に保存すると `…_書込.pdf`(同名があれば `_書込_2.pdf`)。チェック完了では `_書込` を外して元の名前に戻す(`doneName_`)

アプリの一覧(出荷日ごとのまとめ、作業指示一覧)もこの名前を分解して作っている。**名前の形を変えるときは、Sort.js・Code.js(`workSheet`)・Index.html(`parseSortName`)の3か所を合わせること。**

### 4.2 コピーの「説明」欄

1行1項目の `名前:値`。1行目は得意先コード。

```
得意先コード:5200
数量:40
容器No:HXP84961~HXP85000
時間指定:9:00以降
品名:新軽量47L (20kg)
容器サイズ:20
```

訂正版のときは、さらに次の行が付く(→ 7.14)。

```
前の版:<前の版のファイルID>
前の版の出荷日:26.10.07
前の版の状態:未 / 途中保存 / 完了
結合:済            ← アプリで前の版のページをつないだあと
```

- 振り分けがコピーを作るときに書く(`extractOrderInfo_` → `writeInfo_`)
- 得意先コードがあるので、マスタの会社名が直されたら **OCR をやり直さずに**コピーの名前を直せる(`renameCopiesFromMaster_`)
- 数量などは作業指示一覧(簡易版)に使う。古いコピーは `fillCopyInfo_` が残り時間で読み足す。数量が読めなかったものには `_読めず:1` を付けて、毎回読み直さないようにしている
- 以前の形式(`得意先コード:5200` の1行だけ)も `readInfo_` でそのまま読める
- 別に保存・チェック完了でも説明欄を引き継ぐ(完了したものも作業指示一覧に出すため)

### 4.3 ファイルのプロパティ(Drive の custom properties)

| キー | 値 | 意味 |
|---|---|---|
| `shijishoPen` | `saved` | 上書き保存したが、まだチェック完了していない(=途中保存) |
| `shijishoPenAt` | ISO 日時 | 最後に上書きした時刻 |

アプリの「途中保存 N件」と一覧の橙色の印はこれを見る(`savedQuery_`)。
印の仕組みより前に上書きされたものは、振り分けが元の指図書と md5 を比べて印を付け直した(`markSavedCopies_`)。

### 4.4 棚(書き込みを後から直すためのデータ)

保存した PDF では書き込みが画像として焼き込まれるので、そのままでは1本ずつ消したり直したりできない。
そこで上書き・別に保存のとき、棚フォルダに2つ置く。

| ファイル | 中身 |
|---|---|
| `<ファイルID>.base.pdf` | 書き込む前の PDF。**初めて上書きするときに、サーバー側で上書き前の中身を写す**(タブレットからは送らない) |
| `<ファイルID>.marks.json` | 書き込みの一覧(線・レ点・ハンコの座標)と、保存したファイルの md5 |

- 棚の2つの ID は、保存したファイル自身のプロパティ `shelfBase` / `shelfMarks` にも持たせる。開く・保存するときは名前で探さずに ID で直接読む(ID の無い以前のものは名前で探す)
- 一度も保存していないファイル(途中保存の印なし)は、開くときに棚を探さない
- 開くとき(`loadPdf`)に棚があり、md5 が今のファイルと一致すれば、書き込み前 PDF + 一覧を返す。画面ではそれを重ねて表示するので、書き込みを1つずつ直せる
- md5 が違う(アプリの外で差し替えられた)ときは棚を使わず、ファイルをそのまま開く
- チェック完了したら棚の2つもゴミ箱へ(`trashShelf_`)
- 棚の書き込み前 PDF が消えていたら、サーバーは `NEED_BASE` を返し、アプリが手元の PDF を送り直す
- 以前は PDF の中に添付ファイルとして入れていた(`shijisho-pen-base.pdf` / `shijisho-pen-marks.json`)。その形式も開けて、次の上書きで棚へ移る(`baseSource: 'embedded'`)

### 4.5 スクリプトプロパティ

| キー | 用途 |
|---|---|
| `ROOT_FOLDER_ID` | アプリの起点フォルダ(未設定なら `DEFAULT_FOLDER_ID`) |
| `SHELF_FOLDER_ID` | 棚フォルダの ID |
| `CUSTOMER_MASTER_ID` | 得意先マスタの ID |
| `MASTER_SEED_VERSION` | 出荷実績を取り込んだ版。`MasterSeed.js` の `MASTER_SEED_VERSION` と同じなら取り込み済み |

| `SORT_DAILY_OFF` | `removeSortTrigger` で止めた印。あると `runSort` はトリガーを入れ直さない |
| `SORT_CONTINUE_TRIGGER` | 時間切れの続き用(1回きり)トリガーの ID |

## 5. 主要ファイルの中身

### 5.1 `appsscript.json`

- タイムゾーン Asia/Tokyo、V8、Drive 高度サービス v3(識別子 `Drive`)
- スコープ: `drive`、`script.external_request`(OCR 結果の export とマスタの CSV 取得)、`script.scriptapp`(トリガー)。
  `documents` スコープは使わない(4.、7.4 参照)
- ウェブアプリ: `executeAs: USER_DEPLOYING`(デプロイした人の権限で Drive を触る)、`access: DOMAIN`(組織内のみ)

### 5.2 `Code.js` — アプリのサーバー側

画面から `google.script.run` で呼ばれる公開関数:

| 関数 | 役目 |
|---|---|
| `doGet()` | `Index.html` を返す。埋め込み枠で動けるよう `ALLOWALL` |
| `getFolderInfo()` / `setFolderId(id)` | 起点フォルダの名前 / 変更 |
| `listFolder(folderId)` | フォルダ1階層ぶんのサブフォルダと PDF、パンくず |
| `savedCount()` | 途中保存の総数。一覧と並べて呼び、届いたら一番上に出す |
| `listSavedPdfs()` | 途中保存のファイルを全部(要確認に移ったものも)。どのフォルダにあるか付き |
| `searchPdfs(keyword)` | 起点の配下すべてをファイル名で検索 |
| `workSheet(dayKey)` | 作業指示一覧(簡易版)。容器サイズ別フォルダ・要確認・チェック完了を横断し、その日の行と、選べる日にちの一覧を返す |
| `loadPdf(fileId)` | PDF を base64 で返す。棚が有効なら書き込み前 PDF と書き込み一覧を返す |
| `savePdf(req)` | 保存。`req.mode` が `overwrite`(上書き)/ `copy`(別に保存)/ `done`(チェック完了) |
| `saveDiagLog(text)` | ペンの診断記録を棚の `ログ/` に置く |

`savePdf` の3つのモード:

- **overwrite** … 棚に書き込み前 PDF が無ければ先に置く → ファイル本体を差し替え、途中保存の印を付ける → 書き込み一覧と md5 を棚へ
- **copy** … 同じフォルダに `_書込.pdf` を作る(説明欄と途中保存の印を付ける)→ 新しいファイル ID で棚を作る
- **done** … `◆チェック完了/<出荷日の年>年/<出荷日の月>月/<容器サイズ>` に作る(サイズはコピーの親フォルダ名。要確認から完了したときは説明欄から)。**作れたことを確かめてから**元のコピーをゴミ箱へ(完全削除ではないので30日は戻せる)→ 棚もゴミ箱へ

スクリプトロックは、新しいファイルの名前を決めて作るところ(別に保存・チェック完了)だけにかけている。保存全体にかけると、何台かで同時に保存したとき互いに待たされるため。

### 5.3 `Index.html` — アプリの画面

外部ライブラリは cdnjs の **pdf.js 3.11.174**(表示)と **pdf-lib 1.17.1**(PDF 作成)だけ。フォントは使う字だけを抜き出して base64 で埋め込んでいる(社内から Google Fonts が塞がれていても字が変わらない)。

主な部分:

| 部分 | 中身 |
|---|---|
| 表示 | 下に PDF のキャンバス、上に書き込みのキャンバスを重ねる。キャンバスの画素数は 1,200万まで(`MAX_CANVAS_PIXELS`、iPad のメモリ対策) |
| 道具 | ペン(3色・3太さ・筆圧で 0.8〜1.2 倍)、レ点(1タップで形を押す)、消しゴム(触れた書き込みを1つ消す)、戻す、ページ消去 |
| ハンコ | 日付印(前田・森・落合。丸を横線で分け、上に名前・下に日付。江戸文字 `StampEdo`)と、シャチハタ(名前だけの丸印。古印体風 `SealKoin`、A4 で直径 9.5mm) |
| 拡大縮小 | 2本指のピンチ・移動。ペンが触れたらペンを優先 |
| 一覧(左の引き出し) | 容器サイズのフォルダ → 出荷日(件数・途中保存の数・今日/明日) → その日の表(依頼No./出荷先/状態)。検索、途中保存だけの一覧 |
| 作業指示一覧(簡易版) | 全画面。日にちを選ぶと、サイズごとに 依頼No./出荷先/品名/数量/容器No./時間指定/状態 と、件数・本数の合計 |
| 現品写真 | チェック完了のときだけ、撮った写真を PDF の末尾に1枚1ページで足す |
| 保存 | 上書き保存 / 別に保存 / チェック完了 / 保存せず閉じる。書き込みは pdf-lib で PDF に焼き込み、別に書き込み一覧(JSON)も送る |
| 診断記録 | 「書きにくいときの記録を送る」ボタン。ペンの生の入力とアプリの扱いを記録して `saveDiagLog` へ |

書き込みの座標・太さは**紙の幅に対する割合**で持つ。画面の大きさや拡大率が変わっても、書き出した PDF で同じ見た目になる。

### 5.4 `Sort.js` — 振り分け

公開関数(エディタから実行するもの)は4つだけ:

| 関数 | 役目 |
|---|---|
| `runSort()` | 振り分けを1回ぶん回す。毎朝のトリガーもこれ |
| `installSortTrigger()` | 毎朝6時(`SORT_DAILY_HOUR`)のトリガーを入れる。`runSort` も入っていなければ自分で入れるので、ふだんは不要 |
| `removeSortTrigger()` | 自動実行を止める(止めた印を残す) |
| `openCustomerMaster()` | 得意先マスタの URL をログに出す |

`runSort` の順番(順番に意味がある):

1. スクリプトロック(毎朝のぶんと続きのぶんが重ならないように)。続き用トリガーの後始末
2. `applyMasterSeed_` … 出荷実績をマスタへ取り込む(版ごとに1回だけ)
3. `loadCustomerMaster_` … マスタを読む。**読めなければここで止める**(崩れた OCR 名のまま大量にコピーしないため)
4. `ensureDailyTrigger_` … 毎朝のトリガーが無ければ入れる
5. `sortCheckedFiles_` … チェック完了を「出荷日の月 / 容器サイズ」に並べ直す(月が違うもの、月フォルダ直下・「その他」のもの)。見るのは DONE_LOOKBACK_MONTHS か月前から2か月先まで。サイズは今いるサイズのフォルダ → 説明欄(容器サイズ → 品名 → 容器No. の頭)→ PDF の読み直し(1回2分まで。読めなかったものは印を付けて「その他」)
   `trashCheckedLeftovers_` … チェック完了済みなのに容器種類別・要確認に残っているコピーをゴミ箱へ(途中保存と `_書込` は触らない)
6. `moveOverdueCopies_` … 出荷日が昨日以前のコピーを要確認へ
7. `sortMonths_` … 当月から2か月先までの元フォルダを見て、まだのものを OCR してコピー(時間の予算は5分)
8. `renameCopiesFromMaster_` … マスタの会社名に合わせて、コピーとチェック完了の名前を直す(`_書込`・`_2` は残す。説明欄にコードが無いチェック完了は PDF を読み直してコードを取る、1回1分まで)
9. `markSavedCopies_` … 印の無い上書き済みコピーに途中保存の印
10. `appendUnknownCustomers_` … マスタに無い得意先コードを表に足す(会社名は空欄)
11. `fillCopyInfo_` … 説明欄に数量などが無いコピーを残り時間で読み足す
12. 残りがあれば2分後に続きを予約(`scheduleContinue_`)。結果とメモをログに出す

後段の処理は `step_` で包んであり、1つ失敗しても他は止まらない(結果に「失敗: …」と残る)。

1件の振り分け(`sortOne_`):

- 出荷日が**今日以前**なら何もしない(OCR の前に名前だけで判定)
- 容器種類別と、チェック完了(今月から3か月ぶん)に同じ `出荷日_依頼No_` があれば飛ばす
- OCR(`readPdfText_`)… PDF を Google ドキュメントに変換し、Drive API の export で本文を取り、変換物は必ず捨てる。1件17秒ほど
- 容器サイズ(`extractSizeKg_`)… 品名の `(20kg)` を探す。複数に割れたら容量 `47L` から引く(`LITER_TO_KG`)。それでも決まらなければ一番多い値。サイズのフォルダが無ければスキップして報告
- 得意先コード(`extractCustomerCode_`)… `出荷先` の直後の英数字3〜5桁(数字を含むもの)。全角は半角にしてから読む
- 会社名(`lookupCustomer_`)… マスタを完全一致で引き、無ければ OCR の読み違い(O↔0、I↔1)を直した形で引く。どちらでも2社に当たるなら決めない

### 5.5 `MasterSeed.js` — 得意先マスタの元データ

- 2024年度・2025年度の出荷実績(Excel 2本)から作った `[出荷先コード, 略称, 最終出荷日, 出荷件数]` × 1,074件
- 名前が途中で変わったコードは、いちばん新しい出荷のときの名前。名前が空欄のコード(918)は入れていない
- `applyMasterSeed_` がマスタ表へ取り込む: B列(会社名)を実績の略称にし、元の B列は C列(以前の名前)へ残す。D列に「出荷実績 N件・最終 日付」
- `MASTER_SEED_VERSION` を変えるともう一度取り込む

## 7. 設計判断(なぜこうしたか)

### 7.1 元の指図書には触らず、コピーで作業する

元の PDF は本社から届いた原本なので、振り分けは読むだけ。書き込み・名前替え・移動・削除はすべてコピー側で行う。
振り分けを何度やり直しても原本は無事で、コピーを消しても作り直せる。

### 7.2 日にちやコピー済みの判定はファイル名で行い、フォルダは増やさない

出荷日のフォルダを Drive に作らず、名前の先頭 `出荷日_依頼No_` から判定・表示する。
Drive の `name contains` 検索は括弧を含む名前で取りこぼし、二重コピーが起きたことがある。そのため、フォルダの中身を一度に全部読んで手元で突き合わせている(`collectDestNames_`)。

### 7.3 チェック完了も「済み」として見る

以前は容器種類別だけを見ていたため、チェック完了して消えたコピーを次の実行で作り直していた(同じ指図書を二度チェックし、チェック完了に2つ入った)。
今は `◆チェック完了` の出荷日の月で2か月前から2か月先までも見る(`DONE_LOOKBACK_MONTHS`・`SORT_MONTHS_AHEAD`)。

### 7.4 OCR は Google ドキュメント変換 + Drive API の export

GAS は PDF の文字を直接読めない。`DocumentApp` で本文を読むと `documents` スコープが増え、再認可が必要になって、ウェブアプリ側にも影響が出る。
Drive API の export なら、既にある `drive` スコープで済む。変換物は自分のマイドライブに作り、読み終えたら必ず捨てる(共有ドライブを汚さない)。

### 7.5 会社名は OCR ではなく得意先マスタから付ける

OCR の会社名は崩れる(`(工關東 群馬営業所` → 本当は `エネサンス関東 群馬`)。得意先コードの方が安定して読めるので、コードでマスタを引く。
コードは説明欄に残すので、マスタを直せば OCR なしで名前を付け直せる。
マスタは現場の人がスプレッドシートの B列を書くだけで直せる形にした(関数の実行や設定の変更を求めない)。

### 7.6 マスタの会社名は出荷実績の略称にそろえた

正式名(`岩谷産業株式会社 淡路工場`)より略称(`岩谷 淡路`)の方が、現場で見慣れていて短い。そのため 2024〜2025年度の出荷実績の略称にそろえた。
実績の略称にはばらつきがある(`HL近畿 田辺`、`(株)ENK …`、字数で切れた `中部プロパン供給セン` など)。直したいものは B列を書き換える。

得意先コードは、文字をそのまま使って比べる(`I774` と `1774` は別の得意先)。読み違いの補正(O→0、I→1)は、完全一致で見つからないときだけ行い、2社に当たる場合は決めない。

### 7.7 片付けは消す前に確かめ、完全削除はしない

- チェック完了: 完了フォルダにファイルが**できたのを確かめてから**、元のコピーをゴミ箱へ
- 重複の片付け: 途中保存したものと `_書込` は、書き込みがあるので触らない
- どれもゴミ箱(30日間は戻せる)。以前、崩れた名前のコピーを片付ける関数が、正しいコピーまで消したことがある。それ以来、使い捨ての片付け関数は置かず、毎回の `runSort` の中で条件を絞って行う

### 7.8 毎朝の自動実行を `runSort` 自身が確かめる

以前はトリガーを入れる関数を別に実行する必要があった。初回は権限不足で失敗し、そのまま気づかれず、出荷日を過ぎたコピーが要確認へ移らなかった。
今は `runSort` のたびにトリガーの有無を確かめ、無ければ入れる。止めたいときは `removeSortTrigger`(止めた印を残すので入れ直さない)。

片付け(重複の削除・要確認への移動)は振り分けより先に行う。GAS の実行時間の上限は6分で、振り分けが時間いっぱいまで回った場合、あとの処理は上限で止まってしまうことがある。時間のかかる数量の読み足しは最後に回し、残った分は2分後の続きの実行に回す。

### 7.9 書き込みを後から直せるように「棚」を別ファイルで持つ

上書きしたあとにミスしたレ点を直したい、という要望から。はじめは書き込み前 PDF と一覧を PDF の中に添付していた。しかしファイルが倍の大きさになり、開くのも保存するのも遅くなった。
そこで Drive の別ファイル(棚)に分けた。書き込み前 PDF は初回の上書きのときにサーバー側で写すので、タブレットから送る量は変わらない。md5 で「アプリの外で差し替えられていないか」を確かめてから使う。

### 7.10 ペン入力(iPad)まわり

書きにくい・2画目が出ない、という問題に対して、診断記録を取って原因を突き止めた。

- **2画目が出ない** … iOS が素早い2回目のタッチをダブルタップ(拡大)として飲み込み、アプリにペンの入力が届いていなかった。紙の上の touch イベントをすべて `preventDefault` し、`touch-action: none` にして解決
- **手のひら** … ペンが一度でも触れたら、ペン以外の入力は書き込みに使わない。ペンを離してからしばらくは指の動きも無視する
- **ピンチ** … 指の動きが少し大きくなってから拡大縮小を始める(書き始めを奪わない)
- **描画** … 次のフレームでまとめて描き直す(`requestAnimationFrame`)。iPad でキャンバスの更新が画面に出ないことがあるので、不透明度をわずかに揺らして反映させている
- **筆圧** … この iPad のペンは筆圧がほぼ一定(0.12)で届くので、太さの変化は 0.8〜1.2 倍に抑えてなめらかにしている

診断ボタンは、問題が再発しなければ外してよい。

### 7.11 確認ダイアログは自前

GAS のウェブアプリは別オリジンの埋め込み枠で動く。そのため `confirm()` はブロックされ、すぐ false が返る。確認は画面内のダイアログ(`ask()`)で行う。

### 7.12 作業指示一覧(簡易版)はコピーから作る

正式な作業指示一覧表は当日にしか発行されない。そのため、振り分けたコピーの名前と説明欄から、前もって日ごとの一覧を作れるようにした。
同じ指図書が2か所にあるときは、完了 > 途中保存 > 未 の順に1行だけ出す。
あくまで簡易版で、正式な一覧表の代わりではない(画面にもそう書いている)。

### 7.13 チェック完了は月の中を容器サイズで分け、読むときはまとめて問い合わせる

1か月で数百件のチェック完了が1つのフォルダに溜まると、保存時の同名確認、作業指示一覧、振り分けの「済み」判定が遅くなった。
- 保存先を `<月>/<容器サイズ>` に分けた。フォルダ ID は CacheService に6時間覚えておき、保存のたびに名前で探さない
- 複数フォルダの中身は、親を20個ずつ OR でつないだ1回の問い合わせで読む(`listPdfMetaIn_`)
- 途中保存の数は、全ドライブではなく指図書のある共有ドライブだけを探し(`withSavedScope_`)、一覧とは別に取って後から出す
- フォルダの名前・親(パンくず)は1時間、容器サイズのフォルダの並びとチェック完了のフォルダの並びは10分、CacheService に覚えておく
- 開く・保存の Drive 呼び出しを減らした(棚の ID をファイルのプロパティに持つ、md5 は手元で計算、メタデータは1回で取る)。キャッシュが温まった状態で、一覧1回・開く2回・2回目以降の上書き4回・チェック完了4回ほど
- アプリは一度開いたフォルダの中身を覚えておき、次はそれを先に出してから裏で取り直す
- 振り分けは決めた容器サイズを説明欄(`容器サイズ`)に残す。チェック完了の仕分けはまずこれを見る
- サイズが分からない完了ファイルは、品名 → 容器No. の頭の英字(`HEP` など。容器サイズのフォルダにあるコピーから対応を覚え、割れたものは使わない)の順で引く

### 7.14 訂正版は前の版とつないで1つにする

訂正版は「同じ依頼No. で出荷日が違う指図書が後から届く」形で来る(例: 26-10749-0(1) が 10/07 で届き、翌日 10/08 で届き直す)。
以前は別の仕事として2つともコピーされ、2つともチェックされていた。

- **振り分け**(`buildRevisionIndex_` / `sortOne_`)… 同じ依頼No. の元ファイルは一番新しく届いたものだけをコピーする。今あるコピー・完了ファイルに同じ依頼No. で出荷日の違うものがあれば、それを「前の版」として新しいコピーの説明欄に結ぶ。前の版がまだチェック前(未・途中保存)ならそのコピーはゴミ箱へ(30日は読める)。完了済みならそのまま残す
- **アプリ**(`openRevision` / `mergeRevision`)… 訂正版を最初に開いたとき、訂正版のページの後ろに前の版のページ(書き込み・チェック済みのものはそのまま)をつなぎ、Drive にも保存して `結合:済` を付ける。前の版のページの上の余白に「前の版 10月7日出荷(途中保存) 参考」の札を付ける。前の版がさらに訂正版でまだつないでいなければ、その前もたどる(3つまで)
- つなぐのをアプリで行うのは、GAS のサーバー側には PDF をつなぐ手段が無く(pdf-lib を読み込んでも非同期の処理を確実に待てない)、アプリでは PDF を作るのに pdf-lib を既に使っているため
- 一覧・作業指示一覧には「訂正版」の札を出す

### 7.15 フォントは使う字だけ埋め込む

ハンコの字は `前田森落合` と数字だけを抜き出して埋め込んでいる(日付印は Reggae One、シャチハタは Zen Antique。どちらも SIL OFL)。
数 KB で済み、社内ネットワークや端末のフォントに左右されない。人を増やすときは、その字を含めて抜き出し直す必要がある。
